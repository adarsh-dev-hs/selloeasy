An **Architecture Decision Record (ADR)** captures one decision: its context, the choice, its consequences and the
alternatives considered. SelloEasy records every trade-off and optimization as an ADR, so the reasons survive
longer than the conversation that produced them. The trade-off table in the implementation plan (§28) is the
origin of most of these records.

## Format

Each ADR follows the same structure:

```md
---
title: ADR-000N — <decision>
description: <one line>
---

**Status:** Accepted | Superseded by ADR-00xx · **Date:** YYYY-MM-DD

## Context

## Decision

## Consequences

## Alternatives considered

## Revisit when
```

## Process

- Any change that introduces a trade-off (a new dependency, a deliberate limitation, a performance shortcut, a
  security compromise) adds or updates an ADR in the same change.
- ADRs are not rewritten when circumstances change. A new ADR supersedes the old one, and the old one's status is
  updated to "Superseded by ADR-00xx".
- Non-obvious code that follows an ADR points to it in a comment, e.g. `// ADR-0005: stable ordering for offset pagination`.
